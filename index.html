IV
Section four — Editorial

Harness vs. agent: a necessary distinction

The Harness

Open-ended runtime infrastructure

A harness like Claude Code encodes no workflow logic. There's no predefined graph. The model gets a ReAct loop, a bag of tools, and the freedom to decide what to do next at every step. Read a file, run a command, search the web, edit code, spawn a subagent — all chosen dynamically by the model in the moment.

The harness doesn't prescribe what the agent should do. It provides the infrastructure for the agent to do whatever it decides. It's pure runtime scaffolding: guardrails, persistence, observability, tool execution — not business logic.

  • → No predefined graph or DAG
  • → Model is the sole decision-maker at each step
  • → General-purpose tool bag, not task-specific
  • → Open-ended: can solve problems it was never designed for
  • → 5,000–20,000 lines of custom infrastructure
Examples Claude Code · Cursor · Windsurf · Devin · OpenAI Codex
The Structured Workflow

Predefined graph-based orchestration

LangGraph and CrewAI encode workflow logic in the graph structure. You draw nodes, edges, and conditions at build time. The flow is predetermined: classify → research → draft → review → publish. Powerful for known pipelines, but the topology is fixed before the model ever runs.

These frameworks are excellent components inside certain layers of a harness — a structured sub-workflow that an open-ended agent delegates to. But wrapping that in broader orchestration, guardrails, and persistence is still harness work these tools don't address.

  • ◇ Predefined graph with nodes and edges
  • ◇ Developer defines the decision topology
  • ◇ Task-specific tools bound to specific nodes
  • ◇ Scoped: solves the class of problems it was designed for
  • ◇ Framework handles much of the boilerplate
Examples LangGraph · CrewAI · AutoGen · LlamaIndex Workflows
∴
You don't build harnesses with LangGraph. You build structured agent workflows with LangGraph, and you build harnesses around and beneath them. The tools that map to harness-building are lower-level: Temporal for durable execution, a simple ReAct loop you write yourself, a tool registry, and a lot of custom glue. The reason production harnesses are thousands of lines is precisely because no framework handles open-ended agent infrastructure well — you're stitching it together from primitives.
Technical Sidebar

ReAct vs. CodeAct vs. the hybrid

Pattern One

ReAct

Reason → Act (tool call) → Observe. The model picks from a predefined set of typed tools at each step. Five tools means five possible actions. The harness gates every call through a permission system.

1 Model reasons about next step
2 Selects tool from registry
3 Permission gate checks call
4 Tool executes in sandbox
5 Result feeds back as context
⟳ Repeat until done
Tradeoff
✦ Maximum control & auditability
✧ Constrained to pre-built tool vocabulary
Pattern Two

CodeAct

The model writes arbitrary code as its action. The action space is the entire programming language — loops, conditionals, library calls, error handling, composition. No tool registry limits what's possible.

1 Model reasons about next step
2 Writes executable code block
3 Sandbox executes code
4 stdout/stderr feeds back
5 Model iterates or composes
⟳ Repeat until done
Tradeoff
✦ Maximum expressiveness & composability
✧ Harder to sandbox, audit, and permission-gate
In Practice

The hybrid

Claude Code uses ReAct with typed tools — but one of those tools is bash, a CodeAct escape hatch. The model gets auditability by default and arbitrary code execution when it needs it, all through the same permission gate.

1 Model reasons about next step
2 Picks typed tool OR writes code
3 Same permission gate for both
4 Read-only tools run concurrently
5 Mutating tools run sequentially
⟳ Repeat until done
Tradeoff
✦ Best of both: control + expressiveness
✧ Permission design must handle both modes
※

CodeAct is not narrower than ReAct — it's arguably more general. ReAct constrains the agent to a fixed tool vocabulary defined at build time. CodeAct gives the agent the entire language as its action space. The tradeoff isn't capability but governance: structured tool calls are easier to allowlist, audit, rate-limit, and roll back. A hybrid like Claude Code resolves this by routing most actions through typed tools and reserving code execution for when the typed tools aren't enough.

Warning — Editorial

The agent / workflow trap

People don't do only one thing. A marketer writes copy, pulls reports, submits approvals, diagnoses metric drops, and reallocates budgets — all before lunch. Workflows model processes. Harnesses model people. Build for the workflow, and you trap yourself the moment someone does something you didn't anticipate.

✕
The trap
What goes wrong
01
Workflow masquerading as an agent
You build a LangGraph DAG, call it an "AI agent," and ship it. It handles the 5 use cases you designed for. But real people don't do 5 things — they do 50, in any order, often mid-task. The 6th request breaks the graph. You add a node. The 7th breaks it. By month 3, your "agent" is a brittle state machine with 40 nodes that models a process, not a person.
02
Agent where a workflow would suffice
You build an open-ended CodeAct harness for a task that's actually well-defined — say, invoice processing. The model hallucinates a step, skips validation, and costs you $40K. A simple DAG with hard-coded guardrails would have been safer, cheaper, and deterministic.
03
Premature orchestration lock-in
You encode business logic into the graph topology instead of the prompt. When the process changes — and it always changes — you're refactoring infrastructure, not updating a skill. The harness becomes the bottleneck instead of the enabler.
04
Approval chains hardcoded as agent steps
You model approval logic inside the agent instead of delegating to the system of record (Salesforce, ServiceNow, etc.). When the approval policy changes, you're rewriting agent code instead of updating a Salesforce Approval Process. Two sources of truth that inevitably diverge.
05
Non-durable "agents" that lose state
Your agent kicks off a 12-step process, crashes at step 8, and restarts from scratch — re-sending emails, re-submitting approvals, re-creating assets. Without durable execution, every long-running agent is a ticking bomb of duplicate side effects.
✓
The principles
How to avoid it
01
Model the person, not the process
People are flexible. They context-switch, improvise, and handle exceptions as naturally as routine. If you're building for a person — a marketer, an ops lead, an analyst — build a harness. If you're automating a process that never varies, a workflow is fine. The test: does the user do one thing, or everything?
02
Let systems of record own their logic
Approvals live in Salesforce. Content governance lives in Aprimo. Budget rules live in the ERP. The agent triggers these systems and reacts to their signals. It never reimplements their logic. One source of truth, always.
03
Keep business logic in skills, not topology
When the process changes, you update a skill definition or a prompt — not the orchestration graph. Skills are cheap to add, modify, and delete. Graph nodes are infrastructure. Build to delete.
04
Make durability the default, not an add-on
Every external call should be a durable Temporal Activity from day one. Retrofitting durability onto a running agent is like adding seatbelts to a car while driving. The cost of durability upfront is near zero. The cost of not having it is catastrophic.
05
Use workflows inside harnesses
The resolution isn't either/or. An open-ended harness can delegate to structured sub-workflows when the task calls for it. The agent decides which workflow to invoke. The workflow handles the deterministic execution. Best of both worlds.

Section six — The convergence

CodeAct + Temporal skills: durable by construction

Buildable today

What if generated code was already durable?

Right now, the harness wraps durability around the agent's code from the outside. Temporal sits beneath, catching failures. The agent doesn't know it's durable — the infrastructure makes it so.

Flip that. Create a library of Temporal Activities and Workflow patterns as reusable skills. The agent composes them when generating code. Every building block is already durable, so the generated code is durable by construction.

The agent doesn't need to understand Temporal internals. It just needs to know: when I call an API, I use fetch_with_retry. When I need approval, I use wait_for_approval. When I compose steps, I use run_workflow. Those are skills — and the model composes them like any library.

Skill: Durable Fetch # Agent generates this naturally
result = await fetch_with_retry(
  url="https://api.example.com/data",
  max_attempts=3,
  backoff="exponential"
)
# ↑ This is a Temporal Activity.
# Retries, checkpoints, survives crashes.
Skill: Human Gate # Need human approval? One line.
approved = await wait_for_approval(
  reviewer="ops-team",
  context=result.summary,
  timeout="24h"
)
# ↑ Temporal Signal. Process sleeps,
# wakes on approval. State persists.
Skill: Compose Pipeline # Multi-step pipeline, fully durable
async with run_workflow("etl_pipeline") as wf:
  raw  = await wf.step(extract, source)
  clean = await wf.step(transform, raw)
  await wf.step(load, clean, dest)
# ↑ Each step checkpointed. Crash at
# step 2? Resumes from step 2.

This is buildable today with Temporal skills. You define a set of durable primitives as Temporal Activities — API calls with retry, human gates with signals, pipelines with checkpointed steps. The agent learns to compose them the same way it composes any library. The harness gets thinner because the generated code carries its own durability, retry logic, and state management. The seven layers don't disappear, but the persistence layer folds into the skills, orchestration shifts into generated code, and the harness shrinks to what it should be: guardrails, context, and observability.

Section seven — Applied

Beyond code: a marketing harness

CodeAct, not a pipeline

An open-ended harness for marketing

A marketing harness is not a campaign pipeline. That's LangGraph thinking — predefined steps, fixed topology. A real harness is open-ended: the marketer asks anything, and the agent composes whatever Temporal-backed Aprimo and Salesforce skills it needs on the fly.

Think Claude Code, but for marketing. The agent gets a bag of durable skills — search_dam, submit_for_review, create_campaign, pull_metrics, update_lead_scores — and writes CodeAct that composes them dynamically based on what the marketer needs right now.

No predefined workflow. No fixed graph. The model reasons, picks skills, writes durable code, and executes. The marketer's intent is the only input. The agent figures out the rest.

Request "Find assets and draft social posts"

The agent reasons about the request, then writes CodeAct that composes Aprimo skills — no predefined template told it to do this in this order.

Agent-Generated CodeAct # Agent decides: search → filter → generate
assets = await search_dam(
  tags=["enterprise", "product-shot"],

# Agent decides to check brand compliance
for asset in assets:
  await check_brand_compliance(asset)

variants = []
for tone in ["urgent", "curious", "social-proof"]:

    type="social", tone=tone,
    assets=assets[:2],
    brand_kit="enterprise-voice"
  )
  variants.append(v)
# ↑ Every call is a durable Temporal Activity

Temporal + Salesforce Native Automation

Don't rebuild what Salesforce already does

Salesforce already has Approval Processes, Flow Builder, Assignment Rules, Escalation Rules, Lead Routing, and Platform Events. Teams have spent years configuring them. The agent doesn't replace any of it. It triggers these systems and reacts to their outcomes.

The agent submits an Approval Process request and the Temporal Workflow enters a durable sleep — costing zero compute. When the approver clicks "Approve," a Platform Event fires. Temporal catches the signal, wakes the workflow, and the agent resumes instantly. Same for Flows: a lead assignment Flow runs inside Salesforce, the agent listens for the result and immediately starts the next action.

This means the business logic stays where the business team configured it. When a VP changes the approval threshold from $50K to $75K, or the ops team updates lead routing rules in Flow Builder — the agent adapts automatically because it never owned that logic. One source of truth, always.

No polling. No cron jobs. No reimplemented business rules. The agent sleeps until Salesforce tells it what happened.
